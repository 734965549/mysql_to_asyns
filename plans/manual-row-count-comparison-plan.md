# 任务手动结束与行数对比实施计划

## 1. 目标与范围

为同步任务增加两个相互独立的能力：

1. `FULL` 任务继续自然完成并进入 `COMPLETED`；持续运行的 `ALL` 任务可以由用户在增量阶段点击“结束”，进入新的终态 `STOPPED`。
2. 任务结束后由用户手动点击“对比行数”，后台精确统计源端和目标端的 `COUNT(*)`，保存并展示逐表及任务汇总结果。

行数对比不得由同步完成流程自动触发，也不得因为不一致而修改原任务的 `COMPLETED` 或 `STOPPED` 状态。本功能只核对行数，不比较字段内容、校验和或数据样本。

## 2. 任务结束语义

### 2.1 新增任务状态

新增：

```go
TaskStatusStopped TaskStatus = "STOPPED"
```

状态含义：

- `PAUSED`：临时暂停，允许原任务继续启动。
- `STOPPED`：用户确认本次同步已经结束，不允许原任务再次启动、编辑或设置定时调度；仍允许查看、行数对比、复制新建和删除。
- `COMPLETED`：`FULL` 等一次性任务自然执行完成。

状态排序、API 状态筛选、前端标签和文档需要同步支持 `STOPPED / 已结束`。人工结束不计入自然完成任务数，现有 `tasks_completed` 指标仍只统计 `COMPLETED`。

### 2.2 结束操作

新增接口：

```http
POST /api/tasks/:id/end
```

仅在同时满足以下条件时允许结束：

- `status=RUNNING`
- `mode=ALL`
- `sync_phase=INCREMENTAL_STARTED`

结束过程：

1. 在任务锁内再次校验状态，原子地将任务设为 `STOPPED`，记录 `end_time`、更新 `last_update_time`、清除 Cron/repeat 等调度配置，并从运行时映射中摘除增量服务和任务 runtime。
2. 释放任务锁后依次停止增量订阅与 Sink、关闭任务数据库连接，避免在全局任务锁内等待外部资源。
3. 清理内存运行进度并持久化任务状态，写入 `TASK_STOPPED` 审计事件。
4. 接口在资源优雅关闭完成后返回成功。

停止采用“立即优雅停止”语义：完成当前正在退出的处理和资源关闭，但不捕获新的结束位点，也不等待持续产生的源端写入全部追平。

无任务返回 `404`；模式、阶段或状态不允许时返回 `409`。`StartTask`、更新接口及调度接口必须显式拒绝 `STOPPED`，不能只依赖前端隐藏按钮。

## 3. 手动行数对比

### 3.1 API 与执行方式

新增接口：

```http
POST /api/tasks/:id/row-count-comparison
```

接口只负责校验并启动后台任务，成功返回 `202 Accepted`。允许条件：

- 任务状态为 `COMPLETED` 或 `STOPPED`。
- 任务模式为 `FULL` 或 `ALL`。
- `HasFullSyncEverCompleted()` 为真。
- 目标端为 MySQL。

同一任务已经存在 `CHECKING` 核对时再次请求返回 `409`。核对结束后允许重新执行，新结果覆盖旧结果，不保存历史版本。

核对不能复用已经关闭的同步 runtime。后台任务应按任务自身数据库配置重新创建只读用途的源端和目标端连接：只执行连接、`Ping`、元数据读取和 `SELECT COUNT(*)`，不得创建数据库、修改只读状态、检查 binlog 配置或执行任何 DDL/DML。任务配置中没有单独连接信息时，继续采用现有全局数据源/目标端配置回退规则。

### 3.2 对比范围与 SQL

- 单库、多库、源库到目标库映射沿用现有同步规则。
- 指定表任务只核对 `Tables` 配置范围，并沿用 `TargetTables` 重命名映射。
- 库级任务从源端 `information_schema.TABLES` 获取当前 `BASE TABLE` 列表；目标端独有表不纳入汇总。
- Schema 和表名必须使用反引号转义函数构造，不能直接拼接未转义标识符。
- 每张表执行精确 SQL：

```sql
SELECT COUNT(*) FROM `schema`.`table`
```

- 表与表之间串行处理，避免对大库同时发起大量全表计数；同一张表的源端和目标端计数可以并行执行，以减少两端统计时间差。
- 前端必须提示：源端在结束后仍可能继续写入，所以结果是点击核对期间获得的行数快照，不是事务一致性证明。

### 3.3 持久化结果

在 `ProcessContext` 中新增兼容旧存档的可选字段：

```go
RowCountComparison *RowCountComparison `json:"row_count_comparison,omitempty"`
```

建议数据结构：

```json
{
  "status": "MATCHED",
  "started_at": "2026-07-17T10:00:00+08:00",
  "completed_at": "2026-07-17T10:02:30+08:00",
  "total_tables": 2,
  "checked_tables": 2,
  "matched_tables": 1,
  "mismatched_tables": 1,
  "failed_tables": 0,
  "source_total": 300,
  "target_total": 299,
  "difference": -1,
  "tables": [
    {
      "source_schema": "source_db",
      "source_table": "users",
      "target_schema": "target_db",
      "target_table": "users",
      "source_rows": 100,
      "target_rows": 99,
      "difference": -1,
      "matched": false
    }
  ]
}
```

`difference` 统一定义为“目标端行数减源端行数”。行数使用可空字段区分真实的 `0` 与查询失败时的未知值。

汇总状态：

- `CHECKING`：后台核对进行中。
- `MATCHED`：全部表查询成功且行数一致。
- `MISMATCHED`：全部表查询成功，但至少一张表不一致。
- `PARTIAL`：部分表查询失败，其余结果正常保存。
- `FAILED`：连接、表清单获取失败，或所有表均无法完成核对。

`source_total`、`target_total` 只汇总两端都查询成功的表。后台每完成一张表，就用不可变快照更新内存中的任务结果，供详情接口轮询；`CHECKING` 初始状态和最终状态必须持久化。服务启动时发现存档仍为 `CHECKING`，应改为 `FAILED` 并注明服务重启导致核对中断。

TaskService 维护每个任务的核对 cancel function 和 wait group：重复启动需要被拦截；删除任务或关闭服务时先取消核对并等待连接释放，再关闭任务存储，避免后台 goroutine 写入已经关闭的存储。

## 4. 前端交互

### 4.1 结束按钮

- 保留“暂停”按钮。
- 仅当 `RUNNING + ALL + INCREMENTAL_STARTED` 时显示“结束”按钮。
- 点击后显示二次确认，说明结束为终态、原任务不能重新启动。
- 成功后刷新任务列表和详情，展示 `STOPPED / 已结束`。
- `STOPPED` 任务不显示启动、编辑或定时启动按钮。

### 4.2 对比按钮与结果页

- 任务列表操作区和任务详情页顶部均提供“对比行数”按钮。
- 仅 `COMPLETED`、`STOPPED` 且全量已完成的 MySQL 任务显示该按钮。
- 点击前提示精确 `COUNT(*)` 可能扫描大表；确认后调用后台接口。
- `CHECKING` 时按钮禁用并显示“对比中”，详情页按现有任务详情轮询刷新进度。
- 核对完成后允许再次点击，二次确认后覆盖上一次结果。
- 详情页新增“行数对比”页签，展示：
  - 核对状态和开始/完成时间。
  - 源端总行数、目标端总行数、总差值。
  - 一致、不一致、失败、已核对/总表数。
  - 逐表源端/目标端映射、两端行数、差值、状态和错误信息。

前端状态颜色、文案、筛选项和排序展示统一增加 `STOPPED`。

## 5. 错误处理与兼容性

- 单表计数失败不终止其他表，错误记录到对应表结果。
- 后台任务的失败不得修改原任务的 `COMPLETED` 或 `STOPPED`。
- 旧任务 JSON 没有新字段时按 `nil` 处理，不需要数据库表结构迁移；文件存储和 MySQL 存储仍通过任务 JSON 自动兼容。
- 对比结果不得包含源端或目标端密码、DSN 等敏感信息。
- 删除正在核对的任务时先取消后台核对；结果不再写回已删除任务。
- 当前工作树中已有的全量 V2 和指标相关修改必须保留，不得在实现本计划时覆盖或回退。

## 6. 测试与验收

### 6.1 领域与服务测试

- `STOPPED` 状态字符串、结束时间、调度清理以及 JSON 往返兼容。
- `EndTask` 只接受增量阶段运行中的 `ALL` 任务。
- 结束后增量服务和 runtime 被关闭并从映射移除，任务被持久化且不可重启、编辑或调度。
- 自然完成的 `FULL` 任务仍保持现有 `COMPLETED` 行为。

### 6.2 行数核对测试

使用 `go-sqlmock` 覆盖：

- 单库、多个源库和目标库映射。
- 指定表、库级全部基础表和目标表重命名。
- 两端均为 0、一致、不一致，以及目标多行/少行。
- 源端失败、目标端失败、部分失败和全部失败的汇总状态。
- 包含反引号的标识符被正确转义。
- 后台重复启动返回冲突；完成后重新执行会覆盖旧结果。
- 删除、服务关闭和服务重启时的取消/恢复行为。
- 文件存储和 MySQL JSON 存储能完整保存结果，同时不改变内存中的明文密码处理规则。

### 6.3 API 与前端测试

- 结束接口和行数核对接口的 `202/400/404/409` 响应。
- `GET /api/tasks/:id` 返回脱敏任务配置以及行数核对结果。
- 前端按钮显示条件、`STOPPED` 状态、核对进度和结果表格。
- 大数、0 行、未知行数和单表错误的格式化展示。

## 7. 验收标准

- 同步任务完成时不会自动发起任何行数查询。
- `FULL` 自然完成和 `ALL` 人工结束后都可以手动启动行数核对。
- `ALL` 人工结束后状态明确为 `STOPPED`，且不能重启原任务。
- 点击核对后页面无需长时间保持请求，能够持续看到后台状态和最终逐表结果。
- 行数不一致或核对失败不会改变任务终态。
- 多库和表重命名场景下，源端与目标端表映射正确。
- 服务关闭、任务删除或重复点击不会泄漏 goroutine、数据库连接或产生并发重复核对。
