## 任务管理

### 查看任务列表

任务列表采用后端分页接口获取，支持按页浏览、状态筛选、关键字搜索和排序。

#### 列表接口

```http
GET /api/tasks?page=1&page_size=10&status=RUNNING&keyword=order&sort=created_at_desc
```

#### 返回结构

```json
{
  "total": 123,
  "page": 1,
  "page_size": 10,
  "items": []
}
```

#### 任务时间字段

- `created_at`: 任务创建时间，由后端在任务存档中写入，并对应数据库表 `sys_sync_tasks.created_at`
- `updated_at`: 任务更新时间，由数据库在更新任务记录时自动维护，对应 `sys_sync_tasks.updated_at`

#### 任务存储表结构

任务元数据存储在 `sys_sync_tasks` 中，推荐结构如下：

```sql
CREATE TABLE IF NOT EXISTS sys_sync_tasks (
  pk_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  id VARCHAR(64) NOT NULL,
  name VARCHAR(255),
  content JSON,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (pk_id),
  UNIQUE KEY uk_task_id (id)
);
```

如果你是从旧版本升级，建议由 DBA 统一执行补表脚本，示例：

```sql
ALTER TABLE sys_sync_tasks
  ADD COLUMN created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  ADD COLUMN updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;
```

#### 支持的查询参数

- **page**: 页码，默认 `1`
- **page_size**: 每页条数，默认 `10`
- **status**: 按状态筛选，例如 `RUNNING`
- **keyword**: 关键字搜索，可匹配任务名称、任务 ID、源/目标 schema、表名
- **sort**: 排序字段

#### 支持的排序字段

- `created_at_desc` 创建时间倒序（默认）
- `created_at_asc` 创建时间正序
- `name_asc` 名称正序
- `name_desc` 名称倒序
- `status_asc` 状态正序
- `status_desc` 状态倒序
- `progress_asc` 进度正序
- `progress_desc` 进度倒序

#### 前端行为

- 任务列表顶部提供状态筛选、排序和关键字搜索
- 筛选条件会同步到 URL，刷新页面后会自动恢复
- 翻页和修改筛选条件都会重新请求后端

任务列表显示所有已创建的同步任务，包含以下信息：

- **任务名称**: 任务的唯一标识
- **状态**: 
  - 🟦 待执行 (PENDING)
  - 🟩 执行中 (RUNNING)
  - 🟧 已暂停 (PAUSED)
  - 🟩 已完成 (COMPLETED)
  - 🟥 失败 (FAILED)
- **同步级别**: 库级别 或 表级别
- **源库/目标库**: 数据库信息
- **表数量**: 同步的表数量或"全库"
- **进度**: 执行进度百分比和已处理/总行数

### 任务操作按钮

每个任务提供以下操作：

- **详情**: 查看任务的详细信息
- **编辑**: 编辑任务配置（仅待执行或已暂停状态）
- **启动**: 启动任务（仅待执行或已暂停状态）；全量未完成时会按后端规则拒绝或重新全量，增量阶段可从 checkpoint 继续
- **暂停**: 暂停正在执行的任务；全量阶段会保留 `sync_phase=FULL_STARTED`
- **取消定时**: 取消已设置的 Cron/定时启动（仅 `SCHEDULED` 状态）
- **删除**: 删除任务（仅非执行中状态）

### 任务详情抽屉

点击"详情"按钮可查看任务的完整信息：

**基本信息**:
- 任务ID、任务名称
- 同步级别、同步模式
- 源数据库、目标数据库
- 批量大小、工作线程数

**执行状态**:
- 当前状态、进度百分比
- 已处理行数、总行数
- 当前位置、运行时长
- 开始时间、结束时间

**错误信息**:
- 如果任务失败，显示详细的错误堆栈

**同步表列表**:
- 显示所有同步的表名

### 任务运行时进度接口

任务运行时进度接口用于在任务同步期间获取实时的表级进度信息，包括当前同步到哪张表、每张表的行数、进度百分比、同步速度等。

#### 接口定义

```
GET /api/tasks/:id/progress
```

#### 请求示例

```bash
curl http://localhost:8080/api/tasks/abc123/progress
```

#### 响应示例

```json
{
  "current_table": "production.orders",
  "tables": [
    {
      "schema": "production",
      "table": "users",
      "total_rows": 50000,
      "processed_rows": 50000,
      "progress_pct": 100,
      "speed_rows_sec": 1250.5,
      "status": "completed",
      "started_at": "2026-06-19T10:00:00Z",
      "completed_at": "2026-06-19T10:00:40Z"
    },
    {
      "schema": "production",
      "table": "orders",
      "total_rows": 200000,
      "processed_rows": 85000,
      "progress_pct": 42.5,
      "speed_rows_sec": 980.3,
      "status": "running",
      "started_at": "2026-06-19T10:00:41Z"
    },
    {
      "schema": "production",
      "table": "products",
      "total_rows": 10000,
      "processed_rows": 0,
      "progress_pct": 0,
      "speed_rows_sec": 0,
      "status": "pending"
    }
  ],
  "overall_speed": 1050.8,
  "elapsed_seconds": 127.5,
  "estimated_remain": 119.3,
  "phase": "full",
  "updated_at": "2026-06-19T10:02:08Z"
}
```

#### 响应字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `current_table` | string | 当前正在同步的表，格式 `schema.table` |
| `tables` | array | 所有表的进度列表 |
| `tables[].schema` | string | 源库名 |
| `tables[].table` | string | 表名 |
| `tables[].total_rows` | int64 | 该表估算总行数 |
| `tables[].processed_rows` | int64 | 该表已处理行数 |
| `tables[].progress_pct` | float64 | 该表进度百分比 (0-100) |
| `tables[].speed_rows_sec` | float64 | 该表同步速度（行/秒） |
| `tables[].status` | string | 表状态：`pending` / `running` / `completed` / `failed` |
| `tables[].started_at` | string | 该表开始同步时间（ISO 8601） |
| `tables[].completed_at` | string | 该表完成时间（ISO 8601） |
| `overall_speed` | float64 | 整体同步速度（行/秒） |
| `elapsed_seconds` | float64 | 已耗时（秒） |
| `estimated_remain` | float64 | 预估剩余时间（秒），-1 表示无法估算 |
| `phase` | string | 当前阶段：`full`（全量）/ `incremental`（增量） |
| `updated_at` | string | 最后更新时间（ISO 8601） |

#### 前端轮询建议

- 建议轮询间隔：**1-2 秒**
- 进度数据仅存在于内存中，任务完成/暂停/停止后会被清除
- 任务未运行时调用此接口会返回 404
- 可配合 `GET /api/tasks/:id/metrics` 获取持久化的整体指标

## 高级配置

### 同步模式

**全量同步 (FULL)**:
- 一次性迁移所有数据
- 适合首次同步或数据备份
- 速度快，但不支持实时更新

**增量同步 (INCREMENTAL)**:
- 基于 Binlog 实时同步
- 适合持续的数据复制
- 延迟 < 1秒

**全量+增量 (ALL)**:
- 先执行全量同步
- 然后自动启动增量同步
- 适合首次部署后需要持续同步的场景

### 批量大小 (Batch Size)

**作用**: 控制每次批量处理的行数

**建议值**:
- 小表 (< 100万行): 1000-2000
- 中表 (100万-1000万行): 2000-5000
- 大表 (> 1000万行): 5000-10000

**影响**:
- 批量大小越大，同步速度越快
- 但内存占用也会增加
- 需要根据服务器配置调整

### 表并发数 (Worker Count)

**作用**: 控制并发处理的表数量

**建议值**:
- 小规模同步: 2-4
- 中等规模同步: 4-8
- 大规模同步: 8-16

**注意**:
- 过高的并发数会增加数据库压力
- 建议根据数据库性能调整

### 索引优化

**启用索引优化**:
- 同步前删除非主键索引
- 所有表数据同步完成后按表顺序统一重建，索引创建不会与仍在运行的数据写入并发
- 可以显著提高写入速度

**适用场景**:
- 大表全量同步
- 索引较多的表
- 对同步速度要求高的场景

**注意事项**:
- 会短暂影响查询性能
- 需要足够的临时空间
- 建议在低峰期执行

### Cron 定时启动

任务支持使用 Cron 表达式进行计划启动，适合企业级的周期调度场景。

**支持范围**:
- 标准 cron：例如 `0 9 * * 1-5`，表示每周一到周五 09:00 执行
- 扩展 cron：支持 Quartz 风格常见的 `L`、`W`、`#` 语义
  - `0 0 L * *`：每月最后一天 00:00
  - `0 30 9 * * 1#1`：每月第一个周一 09:30
  - `0 0 10 W * *`：每月最接近 10 号的工作日 10:00

**UI 用法**:
- 在“启动任务”弹窗中输入 cron 表达式
- 可点击快捷模板快速填充常见场景
- 可填写时区，例如 `Asia/Shanghai`

**详情页展示**:
- 原始 cron 表达式
- 时区
- 下一次触发时间

**注意**:
- Cron 模式下实际执行时间由表达式计算，后端会写入下次触发的 `scheduled_at`
- 如果表达式不合法，接口会返回校验错误
- 已设置定时的任务可点击「取消定时」恢复为定时前的状态

### 全量起点位点（无需配置，默认走"无锁取位点"）

**作用**:
- 全量同步开始前，自动执行一次 `SHOW MASTER STATUS` 取到 binlog 位点（P0），
  不再使用 `FLUSH TABLES WITH READ LOCK`，无锁、毫秒级。
- 该位点被持久化为后续增量同步的起点，保证全量期间的所有 DML 都能被增量阶段完整回放。
- ALL 模式下，全量基线扫描完成后还会捕获位点 P1，从 P0 做有界追平（bounded catch-up）到 P1。

**接口传参**:
- 无任何前端开关、无任何任务请求体字段需要配置；该行为对所有任务默认生效。

**历史变更**:
- 老版本曾提供 `enable_consistent_snapshot` 字段以及"严格全局快照 + 长事务连接池"
  模式，现已移除。当前实现统一使用"无锁 `SHOW MASTER STATUS` 取位点 + 全量短查询"，
  不再使用 `FLUSH TABLES WITH READ LOCK`，也避免长事务长期持有源库 `MDL_SHARED_READ`。
  如果你的客户端代码仍在传 `enable_consistent_snapshot` 字段，请直接删除，服务端会忽略。

## 自定义数据库配置

### 为什么要自定义数据库配置？

1. **跨服务器同步**: 源库和目标库在不同的服务器
2. **多源同步**: 每个任务使用不同的源数据库
3. **环境隔离**: 测试环境和生产环境使用不同的配置
4. **权限分离**: 每个任务使用独立的数据库账号

### 配置步骤

#### 1. 开启自定义源数据库

展开"自定义源数据库连接"面板，打开开关：

```
┌─────────────────────────────────────┐
│ ▼ 自定义源数据库连接         [ON]   │
├─────────────────────────────────────┤
│ 主机: [192.168.1.100]             │
│ 端口: [3306]                       │
│ 数据库: [production]                │
│ 用户名: [reader]                    │
│ 密码: [••••••••]                   │
│                                     │
│ [测试连接] [保存配置]               │
└─────────────────────────────────────┘
```

#### 2. 填写连接信息

- **主机**: 数据库服务器地址
- **端口**: MySQL 端口（默认 3306）
- **数据库**: 数据库名称
- **用户名**: 数据库用户名
- **密码**: 数据库密码

#### 3. 测试连接

## 系统配置

### HTTP 服务配置

```
监听地址: 0.0.0.0
监听端口: 8081
```

- **监听地址**: 
  - `0.0.0.0`: 监听所有网络接口
  - `127.0.0.1`: 仅本机访问
- **监听端口**: Web 服务的端口号

### 默认数据库配置

用于元数据浏览（获取数据库和表列表）：

```
默认源库地址: 192.168.1.100
默认目标库地址: 192.168.1.101
调试模式: OFF
```

**说明**:
- 这些配置是默认值，每个任务可以单独覆盖
- 调试模式开启后会输出详细的 SQL 语句

### Redis 状态持久化配置

```
主机: 127.0.0.1
端口: 6379
密码: (留空表示无密码)
数据库索引 (DB): 0
```

**重要性**:
- Redis 用于存储任务状态和 Binlog 位点
- 建议配置高可用的 Redis 集群
- 定期备份 Redis 数据

### 日志配置

```
日志级别: Info
☑ 开启控制台标准输出 (Stdout)
☑ 开启文件持久化输出 (File)
```

**日志级别**:
- Debug: 最详细的日志
- Info: 一般信息（推荐）
- Warn: 警告信息
- Error: 仅错误信息

**输出开关**:
- 控制台输出: 适合开发调试
- 文件输出: 适合生产环境

### 任务数据持久化配置

**持久化模式**:
```
○ 本地文件
● MySQL 数据库
```

**本地文件模式**:
```
数据目录: data
```
- 默认使用文件系统存储
- 适合单机部署
- 数据目录需要有写入权限

**MySQL 数据库模式**:
```
MySQL 主机: 127.0.0.1
端口: 3306
数据库: mysql_to_async
用户名: root
密码: ••••••••
```
- 使用 MySQL 存储任务数据
- 适合需要高可用的场景
- 需要先创建数据库和表结构

## 常见问题

### Q1: 搜索框找不到我想要的数据库/表？

**可能原因**:
- 搜索词拼写错误
- 数据库/表名不包含搜索词
- 大小写不匹配（但系统支持不区分大小写）

**解决方案**:
1. 使用更短的关键词
2. 尝试使用部分匹配（如 "prod" 而不是 "production"）
3. 清除搜索框，查看完整列表

### Q2: 全选按钮没有选中所有数据库/表？

**原因**: 全选按钮基于过滤后的列表操作

**解决方案**:
1. 清除搜索条件
2. 确认显示的列表是完整的
3. 再次点击全选

### Q3: 自定义数据库连接失败？

**可能原因**:
- 主机地址错误
- 端口号不正确
- 用户名或密码错误
- 数据库不存在
- 网络不通

**解决方案**:
1. 使用"测试连接"功能验证配置
2. 检查数据库服务是否运行
3. 确认数据库用户权限
4. 检查网络连接和防火墙设置

### Q4: 表列表为空？

**可能原因**:
- 未选择源数据库
- 数据库连接失败
- 数据库中没有表

**解决方案**:
1. 确保已选择源数据库
2. 点击"刷新"按钮重新加载
3. 检查数据库连接配置
4. 确认源数据库中是否有表

### Q5: 任务创建后无法启动？

**可能原因**:
- 未选择数据库或表
- 目标数据库配置错误
- 数据库权限不足

**解决方案**:
1. 检查任务配置是否完整
2. 验证目标数据库连接
3. 确认数据库用户有足够权限
4. 查看任务详情的错误信息

### Q6: 同步速度很慢？

**可能原因**:
- 批量大小设置过小
- 表并发数设置过低
- 网络延迟高
- 数据库性能瓶颈

**解决方案**:
1. 增大批量大小（建议 2000-5000）
2. 增加表并发数（建议 4-8）
3. 检查网络连接
4. 启用索引优化
5. 优化数据库性能

### Q7: 如何查看同步进度？

**方法**:
1. 在任务列表中查看进度条和百分比
2. 点击"详情"按钮查看详细信息
3. 查看"已处理行数 / 总行数"
4. 查看"当前位置"了解当前同步到哪个表

### Q8: 任务失败后如何重试？

**方法**:
1. 查看任务详情的错误信息
2. 解决问题（如修复连接、权限等）
3. 点击"编辑"按钮修改配置
4. 点击"启动"按钮重新执行

### Q8b: 全量同步暂停后，再点启动会继续吗？

**不会继续全量。**

- 未开启「DDL 前 DROP TABLE」时，同一旧任务会被后端拒绝启动；需开启该开关重建后重新全量，或人工清理目标端后创建/重置任务从头跑
- 开启「DDL 前 DROP TABLE」时，再次启动会重建目标库/目标表并重新全量
- 全量已完成并进入增量阶段时，再启动会从增量 checkpoint 继续

详情见 [全量中断处理与增量恢复指南](FULL_SYNC_RESUME_GUIDE.md)。

### Q9: 能否同时运行多个任务？

**答案**: 可以

**说明**:
- 系统支持多任务并发执行
- 每个任务独立运行
- 建议根据服务器性能控制并发任务数

### Q10: 如何删除任务？

**方法**:
1. 找到要删除的任务
2. 确保任务状态不是"执行中"
3. 点击"删除"按钮
4. 在确认对话框中点击"删除"

**注意**:
- 执行中的任务不能删除
- 删除任务会清空相关数据
- 建议先暂停再删除

## 最佳实践

### 1. 任务命名规范

使用描述性的任务名称：
- ✅ "生产用户表同步-20250325"
- ✅ "订单数据备份-每日"
- ❌ "task1"
- ❌ "同步任务"

### 2. 合理设置批量大小

根据表大小调整：
- 小表: 1000-2000
- 中表: 2000-5000
- 大表: 5000-10000

### 3. 利用搜索功能

**场景**: 需要同步所有用户和订单相关的表

**操作步骤**:
1. 搜索 "user"，全选匹配的表
2. 清除搜索
3. 搜索 "order"，全选匹配的表
4. 完成选择

### 4. 定期检查任务状态

建议：
- 每天查看任务列表
- 关注失败的任务
- 检查同步进度
- 查看错误日志

### 5. 使用自定义配置隔离环境

建议：
- 生产环境: 使用生产数据库配置
- 测试环境: 使用测试数据库配置
- 开发环境: 使用开发数据库配置

### 6. 利用索引优化

适合启用索引优化的场景：
- 大表全量同步
- 索引较多的表
- 对同步速度要求高

不建议启用索引优化的场景：
- 小表同步（影响不大）
- 增量同步（不需要）
- 低峰期执行（不急于完成）

### 7. 监控资源使用

关注以下指标：
- CPU 使用率
- 内存使用量
- 网络流量
- 数据库负载

### 8. 定期备份数据

建议：
- 定期备份目标数据库
- 保留 Binlog 文件
- 备份 Redis 数据
- 保存任务配置

## 界面性能优化建议

### 1. 减少列表项

如果数据库或表数量过多：
- 使用搜索功能过滤
- 分批创建任务
- 避免一次选择过多项

### 2. 合理设置刷新间隔

- 默认每 3 秒刷新一次任务列表
- 可以在代码中调整刷新间隔
- 避免过于频繁的刷新

### 3. 使用浏览器缓存

- 推荐使用 Chrome 或 Firefox
- 启用浏览器缓存
- 避免频繁清除缓存
