# 全量同步性能诊断与 V2 优化方案

> 状态：V2 已实现并完成首轮代码复核；自动化检查通过，真实 MySQL 与 4C8G 性能验收待执行
> 适用范围：MySQL 到 MySQL 的 FULL / ALL 初始全量阶段  
> 默认目标：在 4C8G 目标库上兼顾同步速度、目标负载与数据正确性

## 1. 背景与结论

当前项目已经具备 keyset 分页、表内分片、批量 `INSERT`、事务合并、连接池、目标会话优化和索引延后恢复等能力，并不是一个完全没有性能设计的同步器。

但是，现有优化主要集中在单个读写步骤，尚未形成云迁移服务常见的全局调度和独立读写数据面。在“两张大表、每表 4 个表内 worker”的场景中，实际可能同时存在 8 个目标写入连接，并且各表、各分片之间没有任务级写入预算、工作窃取和动态背压。数值主键分片倾斜、字符串主键预扫描、目标二级索引维护、目标 binlog、同步日志和对象分配等成本叠加后，出现 10 小时仍未完成、而云服务约 4 小时完成的差距是合理的。

静态代码检查确认的主要问题如下：

1. 表级并发和表内并发相乘，缺少任务级目标写入并发上限。
2. 每个分片执行“读一批、写一批、再读下一批”，源读取和目标写入没有解耦。
3. 数值主键按 `MIN(pk)` 到 `MAX(pk)` 等值域切分，稀疏或倾斜主键容易出现长尾分片。
4. 字符串和复合主键在正式复制前需要额外扫描大部分主键索引以生成边界。
5. 无主键表固定为单源读取；当前没有利用安全的“单读多写”流水线。
6. 全量行使用 `map[string]interface{}`，并对 `[]byte` 转换为字符串，产生大量对象和 GC 压力。
7. 批次只按行数和占位符控制，没有按传输字节数、事务字节数和提交延迟控制。
8. 默认批量为 1000 行，并行事务默认每 5 批提交；默认不延后目标二级索引，也不跳过目标 binlog。
9. Prometheus 性能指标虽然已经声明，但全量主路径没有写入读、写、提交、队列和连接等待指标。
10. 逐批 INFO 日志、同步审计文件写入及进度持久化仍会进入数据主路径。

此外，现有并行写入重试存在一个必须优先处理的正确性风险：当同一事务中已经成功写入若干批次，后续批次遇到可重试锁错误时，代码会回滚整个事务，但只重试当前失败批次。之前已写但未提交的批次不会被重新执行，进度却已经增加，存在静默缺数风险。

## 2. 云迁移服务公开能力对照

云服务的内部实现属于黑盒，不能假定其使用了直接存储导入、关闭持久性或其他未公开能力。本方案只采用官方公开资料中可以验证的设计。

- 腾讯云 DTS 将源端全量导出和目标端全量导入设置为独立线程池，默认各 8 个线程，可分别控制并发和 RPS；连续整数主键与字符串、非连续整数主键采用不同的分块方式。参见：[数据迁移常见问题](https://cloud.tencent.com/document/product/571/62986)、[限速（MySQL 系列）](https://cloud.tencent.com/document/product/571/102479)。
- AWS DMS 将并行表/分片数量与目标装载线程分开设置，明确说明两类并发会相乘；其全量 `CommitRate` 默认 10000 行、最高 50000 行，并支持在全量后创建主键或唯一索引。参见：[Full-load task settings](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Tasks.CustomizingTasks.TaskSettings.FullLoad.html)。
- 华为云 DRS 公开说明 MySQL 全量迁移采用行级并行。参见：[MySQL 迁移出现数据膨胀怎么办](https://support.huaweicloud.com/drs_faq/drs_16_1133.html)。
- 阿里云 DTS 将无主键、源/目标性能、目标 CPU 与 I/O、死锁、网络延迟和带宽列为全量迁移慢的主要排查项。参见：[如何解决全量迁移慢或迁移卡住](https://help.aliyun.com/zh/dts/support/what-can-i-do-if-full-data-migration-stops-or-slows-down)。

由此可见，云服务的主要优势并不只是“把线程数调大”，而是将分块、读取、传输、写入、提交和限速作为独立环节管理，并根据源端和目标端能力分别控制。

## 3. V2 总体架构

V2 全量引擎采用任务级流水线，不再让每张表独立创建完整的读写 worker 组。

```text
表与主键分析
    ↓
Chunk 生成队列 ──→ 源读取 Worker 池 ──→ 有界 RowBatch 队列 ──→ 目标写入 Worker 池
                                                              ↓
                                                事务提交、进度、审计和指标
                                                              ↓
                                                    二级索引集中恢复
```

4C8G 平衡预设：

- 全任务最多 4 个源读取 worker。
- 全任务最多 4 个目标写入 worker。
- 任务级缓冲上限 128 MiB，按实际批次估算字节数计费。
- 单条多值 `INSERT` 受 `batch_size`、4 MiB 和 62000 个占位符共同限制。
- 单个事务在 10000 行、32 MiB 或 2 秒任一条件达到时提交。
- Chunk 数量约为读取 worker 数的 8 倍，通过工作窃取消除固定四分片的长尾。

源读取速度高于目标写入速度时，有界队列提供短期缓冲；缓冲达到上限后读取 worker 自动阻塞，形成背压。目标写入恢复后读取会自动继续，不需要通过无限增加连接数维持吞吐。

## 4. 实施内容

### 4.1 P0：正确性修复与性能观测

在任何进一步提速前，先修复事务重试和进度语义：

- 每个写入 worker 保存当前事务包含的全部未提交 `RowBatch`。
- 发生可重试锁错误时回滚并重放整个事务缓冲，而不是只重试最后一个批次。
- 只有事务提交成功后才增加任务、表、分片的已写入行数和字节数。
- 暂停、取消或失败时回滚未提交事务，不把未提交数据计入完成进度。

补充以下观测数据：

- 读取、写入和已提交的行数及字节数。
- 每批读取、排队、SQL 执行和事务提交耗时。
- 当前读/写 worker 数和活跃状态。
- 队列当前字节数、容量和生产者等待时间。
- 连接池 `WaitCount`、`WaitDuration`、`InUse` 和 `Idle`。
- 锁超时、死锁、连接重试和事务重放次数。
- 每个 chunk 的开始时间、结束时间、行数、字节数和平均速度。
- 表结构准备、数据复制和索引恢复各阶段耗时。

任务详情接口返回任务级和表级详细数据。Prometheus 只输出按阶段、操作、结果分类的低基数聚合指标，避免长期使用任务 ID 和表名标签。

### 4.2 P1：任务级 Chunk 调度

建立全任务共享的 chunk 队列和读取 worker 池：

- 自增整数游标列使用细粒度值域 chunk，并通过过量分片降低主键空洞和局部倾斜影响。
- 其他整数、字符串和复合游标列通过一次 PK-only 流式扫描生成近似等行数边界。
- Chunk 数量高于 worker 数，worker 完成当前 chunk 后立即领取下一个，实现工作窃取。
- 不再预先把一张表永久绑定给固定 worker；小表和快 chunk 不占用长期并发配额。
- 无主键表保留一个顺序源游标，读取出的独立批次进入同一个受控目标写入池。
- ALL 模式继续使用全量前捕获的 binlog 位点，由增量阶段追平全量期间的源端变化。

现有 `worker_count` 继续表示同时调度的表数；V2 的实际源读取和目标写入连接数由任务级新配置统一限制。

### 4.3 P2：全量专用 RowBatch

为全量路径增加固定结构的 `RowBatch`，不改变增量事件模型：

```go
type RowBatch struct {
    Schema      string
    Table       string
    Columns     []string
    Rows        [][]any
    StartKey    []any
    EndKey      []any
    ApproxBytes int64
    ChunkID     string
}
```

实施要求：

- 列顺序在分析表结构后固定，扫描和写入不再为每行创建列名 map。
- 游标值独立保存，写入器不再从 map 中二次查找主键。
- 预计算 SQL 前缀、列清单和常见行数的占位符模板。
- 每个目标连接缓存可复用的预处理语句，避免每批重复 PREPARE、EXECUTE、CLOSE。
- 按值类型估算批次字节数，宽行不再统一硬编码为 500 行。
- 增量同步仍使用现有事件 map 和 before-image，不与全量快速路径混用。

### 4.4 P3：目标写入与索引策略

- 全量仍使用普通多值 `INSERT`，目标表必须为空或由 `enable_drop_table_before_ddl=true` 重建。
- 保留主键，在主键顺序 chunk 内按升序读取，避免先删除主键后再整表重建。
- 用户选择“重建目标并快速全量”预设时，同时开启 `optimize_index=true`，延后二级和唯一索引恢复。
- 目标索引恢复继续按表并行、单表内按确定顺序执行，并单独展示阶段进度。
- `FOREIGN_KEY_CHECKS=0` 和 `UNIQUE_CHECKS=0` 保持连接级设置并在连接归还前恢复。
- `enable_skip_binlog` 继续由用户明确开启；不自动修改 `sync_binlog`、`innodb_flush_log_at_trx_commit` 等全局持久性参数。
- 第一版不引入 `LOAD DATA LOCAL INFILE`。待普通多值写入路径完成基准测试后，再将其作为单独、可回退的实验性写入后端评估。

### 4.5 P4：日志、审计与进度路径

- 移除逐批 INFO 日志，改为每 5 秒按任务和表汇总一次吞吐、队列和最慢 chunk。
- 错误、阶段切换、锁重试耗尽和索引恢复失败仍立即记录。
- 数据写审计改为有界异步队列和批量文件写入；队列拥塞时记录丢弃计数和告警，不阻塞数据库数据面。
- 进度存储继续节流，但存储调用移出全局任务互斥锁，避免慢文件或慢 MySQL 存储阻塞 worker。
- 锁外落盘前再次校验快照是否仍有效：比较 `Status` 与 `LastUpdateTime`。若 Pause/End/Fail
  等已在锁内同步保存较新的终态，则丢弃滞后的 RUNNING 快照，避免其反向覆盖 `PAUSED` /
  `STOPPED` / `FAILED` 存档；进程崩溃后重启时不会读到错误状态。

## 5. 配置与接口变更

任务 JSON 新增以下兼容字段：

| 字段 | 类型 | 默认 | 含义 |
|---|---:|---:|---|
| `full_load_engine` | string | `v1` | `v1` 保持旧行为，`v2` 使用新流水线 |
| `full_load_read_workers` | int | `0` | 任务级源读取上限；0 使用自动值，4C8G 预设为 4 |
| `full_load_write_workers` | int | `0` | 任务级目标写入上限；0 使用自动值，4C8G 预设为 4 |
| `full_load_buffer_mb` | int | `0` | 任务级数据队列上限；0 使用 128 MiB |
| `full_load_batch_bytes_mb` | int | `0` | 单条 INSERT 字节上限；0 使用 4 MiB |
| `full_load_commit_rows` | int | `0` | 单事务行数上限；0 使用 10000 |
| `full_load_commit_bytes_mb` | int | `0` | 单事务字节上限；0 使用 32 MiB |

兼容规则：

- V1 完全沿用 `worker_count`、`intra_table_worker_count`、`batch_size` 和 `tx_commit_every_n_parallel` 的当前语义。
- V2 中 `batch_size` 仍是单条 INSERT 的行数上限。
- 如果显式设置旧字段 `tx_commit_every_n_parallel` 且未设置 `full_load_commit_rows`，则提交行数按 `batch_size × tx_commit_every_n_parallel` 推导。
- 新字段需要同步更新 API handler、任务实体、前端表单、配置文档和示例。
- API JSON 旧字段名称保持不变，历史任务缺少新字段时按零值兼容。

前端增加“兼容 V1”“4C8G 平衡”“速度优先”“低目标负载”预设，并展示最终生效值。涉及删除目标或跳过 binlog 的选项必须继续单独确认，不能由性能预设静默开启。

## 6. 测试方案

### 6.1 正确性测试

- 连续整数、稀疏整数、严重倾斜整数、UUID、复合主键和唯一键表。
- 无主键表、空表、小表、超宽表、JSON、TEXT、BLOB、NULL 和大字段。
- 分片边界无重复、无遗漏，目标行数与源端一致。
- 锁超时、死锁、连接断开和提交失败时重放完整未提交事务。
- 暂停和取消时所有未提交事务回滚，任务不能错误进入 FULL_COMPLETED。
- 进度持久化锁外落盘与 Pause/End/Fail 并发时，陈旧 RUNNING 快照不得覆盖
  `PAUSED` / `STOPPED` / `FAILED` 存档（`TestIncrementTaskProgress_SkipsStaleSnapshotAfterLifecycleSave`）。
- 索引删除与恢复失败时状态、错误和残留索引信息可追踪。
- ALL 模式完成全量后，从原始起点继续增量并最终收敛。

### 6.2 并发与资源测试

- 两张表同时同步时，目标活跃写 worker 永不超过任务级上限。
- 多表和表内分片并发不再相乘突破目标预算。
- 队列达到 128 MiB 后源读取阻塞，内存不继续无界增长。
- 快 chunk 完成后可以领取其他 chunk，倾斜表不存在单 worker 长时间拖尾。
- 连接池等待、队列等待和目标提交延迟可以在接口及指标中观察。

### 6.3 性能基准

使用同一源库、同一网络、同一 4C8G 目标库和相同两张表，分别执行 V1、V2 和云服务基准。每组至少运行三次并记录中位数。

必须统计：

- 全量数据读取和写入时间。
- 索引恢复时间。
- ALL 模式增量追平时间。
- 源端读取 MB/s、目标写入 MB/s 和提交 P95。
- 目标 CPU、内存、IOPS、磁盘延迟和活跃连接。
- 同步进程 CPU、RSS、GC 次数和 GC 暂停。

平衡模式验收目标：

- 两张真实表端到端完成时间不超过 4.5 小时。
- 如果无法复现云服务环境，V2 吞吐至少达到 V1 的 2 倍。
- 目标 CPU P95 不超过 70%，活跃目标写会话不超过 4。
- 无持续连接池等待、无持续 IOPS 饱和、无未恢复索引。
- 行数、抽样校验和及最终增量一致性校验全部通过。

## 7. 发布与回退

1. 首先只发布 P0 指标和事务正确性修复，不改变默认全量调度。
2. 通过 `full_load_engine=v2` 灰度一张大表，验证吞吐和目标资源。
3. 灰度两张真实表并与 V1、云服务进行同条件对比。
4. V1 至少保留一个稳定发布周期，V2 异常时允许新任务切回 V1。
5. V2 稳定后再评估是否将新建任务默认引擎改为 V2；历史任务不自动迁移执行引擎。

## 8. 明确不做的事情

- 不恢复当前已经取消的全量断点续传能力。
- 不把全量进度迁移到 Redis；Redis/内存 checkpoint 仍只用于增量 binlog 位点。
- 不通过关闭全局持久性或降低一致性保证换取基准成绩。
- 不改变无主键增量依赖 before-image 和 `FullColumnsStrategy` 的规则。
- 不默认关闭目标 binlog，不静默删除目标库表或索引。
- 不将 FULL 模式伪装成一致快照；FULL 期间的源端变化仍只有 ALL 模式能通过 binlog 追平。

## 9. 2026-07-17 实现复核记录

本轮复核在 V2 初始实现基础上补齐了以下问题：

- 锁冲突继续回滚并重放全部未提交批次；连接错误和 `COMMIT` 结果未知时禁止自动重放普通
  `INSERT`，避免无主键表重复数据。
- 事务等待不到下一批时也会按 2 秒上限提交；暂停、取消和外层 context 取消不能误报成功。
- 复合游标通过 PK-only keyset 边界生成多个 chunk；有符号整数全域分片使用无溢出计算，
  unsigned 整数改走 keyset 边界。
- 读取批次同时受行数和字节数约束，宽行不会先构造超大批次再等待队列背压。
- 每个目标连接增加有界预处理语句缓存；库、表、列名统一转义；行宽异常在执行 SQL 前失败。
- 并行 V2 任务的队列与 worker Gauge 改为差量聚合，任务删除时清理最近一次统计对象。
- 进度持久化改为锁内冻结快照、锁外执行存储 I/O，消除慢存储阻塞全局任务锁的问题。
- 锁外落盘前通过 `shouldPersistAsyncProgressSnapshot` 比较快照与内存任务的 `Status`、
  `LastUpdateTime`，丢弃已被 Pause/End/Fail 等同步存档超越的陈旧进度快照，修复写序竞争。
- V2 数值配置增加安全上限，前端、后端推导和配置文档保持一致。

## 10. 2026-07-19 进度落盘写序修复

`incrementTaskProgress` 为降低 I/O 频率，采用“锁内序列化快照、锁外 `storage.Save`”策略。
Pause/End/Fail 等生命周期操作仍在锁内同步落盘。二者并发时，已出锁但尚未执行的旧 RUNNING
快照可能在终态存档之后落盘，把 `PAUSED` / `STOPPED` / `FAILED` 覆盖回 `RUNNING`；内存状态
正确、下一次保存会纠正，但若此时进程崩溃，重启后会读到错误存档。

修复方式：

- 新增 `shouldPersistAsyncProgressSnapshot`：锁外落盘前再次读取内存任务，仅当 `Status` 与快照
  一致且 `LastUpdateTime` 不早于快照时才执行 `Save`。
- 不引入额外版本号字段；Pause/End/Fail 等路径本来就会更新 `LastUpdateTime` 与终态
  `Status`，足以识别陈旧快照。
- 单元测试：`TestIncrementTaskProgress_SkipsStaleSnapshotAfterLifecycleSave`。
